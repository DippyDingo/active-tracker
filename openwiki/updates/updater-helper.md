# Отдельный процесс-обновлятор

`nodexy_updater_helper.py` собирается в `REDISUpdater.exe` и выполняет единственную задачу: заменить файлы приложения, когда оно уже не работает, и запустить новую версию. Всё, что делает помощник, вынесено в отдельный процесс по необходимости — приложение не может заменить собственный исполняемый файл, пока выполняется.

Файл назван `nodexy_updater_helper.py`, хотя продукт теперь REDIS: имя оставлено, чтобы не ломать ссылки в скрипте сборки и совместимость со старыми установками.

## Зачем отдельный процесс

Установщик Inno Setup отказывается ставить поверх запущенного приложения — он проверяет `AppMutex` и либо просит закрыть программу, либо в тихом режиме прерывается.

Можно было бы поручить установку скрипту (`.bat` или `.vbs`), и раньше так и делалось. От этого отказались: комментарий в `updater.py` фиксирует причину — кавычки в путях и аргументах ломали установку. Отдельный exe принимает аргументы напрямую, без промежуточного разбора оболочкой.

## Перенос в %TEMP%

Первое, что делает помощник при старте:

```python
if getattr(sys, "frozen", False) and os.environ.get("NODEXY_HELPER_TEMP") != "1":
    temp_copy = Path(tempfile.gettempdir()) / f"REDISUpdater-{os.getpid()}.exe"
    shutil.copy2(Path(sys.executable), temp_copy)
    child_env = os.environ.copy()
    child_env["NODEXY_HELPER_TEMP"] = "1"
    subprocess.Popen([str(temp_copy), *sys.argv[1:]], ...)
    return 0
```

Причина в комментарии: помощник **нельзя обновлять, пока он запущен из каталога приложения**. Установщик заменяет все файлы, включая `REDISUpdater.exe`, а работающий процесс держит свой образ открытым. Windows не даст перезаписать запущенный exe.

Поэтому помощник копирует себя в `%TEMP%` с уникальным именем (`REDISUpdater-<pid>.exe`), запускает копию с теми же аргументами и выходит. Копия работает уже не из каталога программы, и файлы можно заменять свободно.

Защита от бесконечной рекурсии — переменная окружения `NODEXY_HELPER_TEMP=1`, которая передаётся дочернему процессу. Без неё копия снова скопировала бы себя, и так до бесконечности.

## Ожидание выхода приложения

```python
deadline = time.monotonic() + 120
while pid_alive(args.pid) and time.monotonic() < deadline:
    time.sleep(0.25)
if pid_alive(args.pid):
    log(log_path, "target pid did not exit within 120 seconds")
    return 3
```

Ожидание ограничено 120 секундами с шагом 250 мс. `pid_alive` использует `psutil.pid_exists`, а при его отсутствии — `os.kill(pid, 0)`.

Проверка именно по PID, а не по имени: имя могло измениться между версиями (`Nodexy.exe` → `REDIS.exe`), а PID — уникальный идентификатор конкретного процесса, который запросил обновление.

После выхода процесса добавляется пауза в одну секунду (`time.sleep(1.0)`), чтобы файловая система гарантированно освободила дескрипторы.

## Вторая проверка: exe всё ещё работает

```python
deadline = time.monotonic() + 30
while target_running(restart) and time.monotonic() < deadline:
    time.sleep(0.5)
if target_running(restart):
    log(log_path, "target executable is still running")
    return 4
```

`target_running(exe)` обходит процессы и сравнивает их `exe` с целевым путём после `resolve()` и `casefold()`.

Это защита от сценария: пользователь закрыл окно, но сразу запустил приложение снова. Процесс с переданным PID завершился, но работает другой экземпляр того же exe — и замена файлов под ним была бы катастрофой. Ожидание до 30 секунд даёт шанс, что он закроется сам.

## Запуск установщика

```python
command = [
    str(setup),
    "/VERYSILENT",
    "/SUPPRESSMSGBOXES",
    "/NORESTART",
    "/SP-",
    "/LOG=" + str(install_log),
    "/DIR=" + str(target_dir),
    "/DISABLEDIRPAGE",
]
```

Разбор флагов:

| Флаг | Назначение |
|---|---|
| `/VERYSILENT` | Полностью без интерфейса |
| `/SUPPRESSMSGBOXES` | Не показывать диалоги |
| `/NORESTART` | Не перезагружать систему |
| `/SP-` | Не показывать предложение установить обновления Inno |
| `/LOG=` | Писать журнал установки |
| `/DIR=` | Явный каталог назначения |
| `/DISABLEDIRPAGE` | Отключить страницу выбора каталога |

### Зачем /DIR и /DISABLEDIRPAGE

Комментарий описывает конкретную проблему: установщик запоминает каталог по `AppId` и при тихом обновлении подхватывает путь из реестра. Если рядом осталась старая параллельная установка, файлы уезжали туда, а запускалась прежняя копия — версия «не менялась».

Поэтому каталог передаётся явно, а страница выбора отключается: без `/DISABLEDIRPAGE` установщик мог бы проигнорировать `/DIR`.

### Запуск без оболочки

`subprocess.run` вызывается с `creationflags=CREATE_NO_WINDOW`, все стандартные потоки — `DEVNULL`, `check=False`. Код возврата читается и записывается в журнал вручную.

Отказ от `shell=True` — принципиален и связан с историей: путь может содержать пробелы, и через оболочку аргументы разбирались неверно.

## Выбор запускаемого файла после установки

Переименование Nodexy → REDIS создало проблему: после установки помощник должен запустить приложение, но имя могло измениться.

```python
candidates = [
    target_dir / "REDIS.exe",
    target_dir / restart.name,
    restart,
    restart.with_name("REDIS.exe"),
]
```

Проверяются четыре варианта в порядке приоритета:

1. `REDIS.exe` в целевом каталоге — текущее имя;
2. исходное имя переданного exe в целевом каталоге;
3. полный путь переданного exe;
4. `REDIS.exe` рядом с переданным путём.

Ожидание до 30 секунд, пока хотя бы один появится: установщик завершился, но файловая система может отставать.

Запускается первое найденное. Логика в том, чтобы искать в **целевом** каталоге, а не по переданному пути: установщик мог установиться в другое место, и путь из аргументов устарел бы.

## Порядок: маркер снимается до запуска

Это самое важное место во всём файле.

```python
# Маркер установки снимается ДО запуска приложения: иначе новая копия
# видит свежий lock и живой helper, считает, что установка идёт, и
# сразу выходит — обновление оставалось бы без запущенного приложения.
lock_path.unlink(missing_ok=True)
subprocess.Popen([str(restart)], ...)
```

Логика: приложение при старте проверяет `install_in_progress()` — есть ли свежий `install.lock` и жив ли помощник. Если бы маркер снимался после запуска, новая копия увидела бы и маркер, и работающий помощник, решила бы, что установка ещё идёт, и вышла по коду 0. Пользователь остался бы без запущенного приложения.

Порядок строго такой: сначала удалить маркер, потом запустить.

Дополнительно `finally` блока `run` тоже удаляет маркер — на случай ошибки на любом шаге.

## Коды возврата

| Код | Значение |
|---|---|
| 0 | Успех или перенос в `%TEMP%` выполнен |
| 1 | Установщик вернул ошибку (или ненулевой код) |
| 2 | Не удалось создать маркер блокировки |
| 3 | Целевой PID не завершился за 120 секунд |
| 4 | Целевой exe всё ещё работает |
| 5 | Файл установщика отсутствует |
| 6 | Запускаемый exe не найден в целевом каталоге |
| 7 | Внутреннее исключение |
| 8 | Не удалось перезапуститься из `%TEMP%` |

Коды 3 и 4 означают «условия не позволили заменить файлы» — в этом случае приложение не пострадало, и обновление можно повторить. Коды 1, 5, 6 и 7 означают проблему с самим обновлением.

Код 8 — особый: если перенос в `%TEMP%` не удался, помощник продолжает работу из каталога приложения, что может привести к невозможности заменить собственный файл при следующем обновлении.

## Журналирование

`log(path, message)` пишет строки с отметкой времени в формате `%Y-%m-%d %H:%M:%S | message`, создавая каталог при необходимости. Ошибки записи журнала подавляются — помощник должен работать даже если писать некуда.

Путь к журналу передаётся аргументом `--log` и указывает на `nodexy_update.log` в каталоге данных. Именно там ищут следы неудачной установки.

Основные события: старт с параметрами, попытка переноса, ожидание PID, запуск установщика, код возврата установщика, запуск приложения.

## Что важно помнить при правке

- Перенос в `%TEMP%` и переменная `NODEXY_HELPER_TEMP` — пара, защищающая от рекурсии. Убирать одну часть без другой нельзя.
- Маркер `install.lock` снимается **до** запуска приложения. Обратный порядок ломает перезапуск.
- Ожидание по PID, а не по имени — имя менялось между версиями.
- Вторая проверка `target_running` защищает от ручного перезапуска во время установки.
- `/DIR` и `/DISABLEDIRPAGE` работают вместе: без второго первый может игнорироваться.
- Установщик запускается без оболочки, со всеми потоками в `DEVNULL`.
- Список `candidates` нужен из-за переименования; при появлении нового имени его надо дополнить.
