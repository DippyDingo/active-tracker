# Схема базы данных и миграции

Вся статистика хранится в одном файле SQLite. Схема намеренно простая: пять таблиц, из которых две содержат время. `Database` — тонкая обёртка над одним соединением, без ORM и без пула; методы либо читают, либо пишут, и почти все изменения времени проходят через одну функцию пакетной записи.

## Подключение и режимы

При создании объекта `Database` последовательно делается следующее:

1. Создаётся каталог родительской папки файла, если его нет.
2. Открывается соединение с `row_factory = sqlite3.Row` — строки доступны и по индексу, и по имени колонки.
3. Устанавливаются три прагмы:
   - `PRAGMA journal_mode=WAL` — журналирование с отдельным файлом `-wal`;
   - `PRAGMA synchronous=NORMAL` — компромисс между надёжностью и скоростью при WAL;
   - `PRAGMA foreign_keys=ON` — включение внешних ключей, которые в SQLite по умолчанию выключены.
4. Выполняется `_SCHEMA` через `executescript` — все таблицы создаются с `IF NOT EXISTS`.
5. Выполняется `_migrate()` для добавления колонок в существующие базы.

Важно, что `CREATE TABLE IF NOT EXISTS` плюс `_migrate` дают самообновляющуюся схему: одно и то же открытие базы работает и для нового файла, и для файла многолетней давности.

## Таблицы

### apps — отслеживаемые приложения

| Колонка | Тип | Ограничения |
|---|---|---|
| `id` | INTEGER | Первичный ключ, автоинкремент |
| `name` | TEXT | NOT NULL |
| `exe_path` | TEXT | NOT NULL, UNIQUE, COLLATE NOCASE |
| `icon` | BLOB | Иконка в PNG, может быть NULL |
| `sort_order` | INTEGER | NOT NULL, по умолчанию 0 |
| `added_at` | TEXT | По умолчанию `datetime('now')` |
| `category_id` | INTEGER | Ссылка на `categories`, ON DELETE SET NULL |

Две детали здесь несут смысл:

- **`COLLATE NOCASE` на `exe_path`** отражает реальность Windows: пути к файлам нечувствительны к регистру. Без этого в базу можно было бы добавить один и тот же exe дважды, набрав путь с другим регистром.
- **`UNIQUE` на `exe_path`** — единственная защита от дублей на уровне схемы. `add_app` полагается на неё и возвращает `None` при `IntegrityError`, вместо того чтобы проверять наличие записи запросом.

### stats — секунды по дням

| Колонка | Тип | Ограничения |
|---|---|---|
| `app_id` | INTEGER | NOT NULL, FK на `apps`, ON DELETE CASCADE |
| `day` | TEXT | NOT NULL, дата в ISO `YYYY-MM-DD` |
| `seconds` | INTEGER | NOT NULL, по умолчанию 0 |

Составной первичный ключ `(app_id, day)` делает запись идемпотентной по адресу: для одного приложения за один день существует ровно одна строка.

### hours — секунды по часам

| Колонка | Тип | Ограничения |
|---|---|---|
| `app_id` | INTEGER | NOT NULL, FK на `apps`, ON DELETE CASCADE |
| `day` | TEXT | NOT NULL |
| `hour` | INTEGER | NOT NULL, 0–23 |
| `seconds` | INTEGER | NOT NULL, по умолчанию 0 |

Первичный ключ — `(app_id, day, hour)`. Ограничение 0–23 не задано в схеме, но `get_hours` его проверяет при чтении: строки с `hour` вне диапазона пропускаются, а не ломают график.

### settings — плоское хранилище

| Колонка | Тип | Ограничения |
|---|---|---|
| `key` | TEXT | Первичный ключ |
| `value` | TEXT | NOT NULL |

Здесь лежат все пользовательские настройки и маркеры одноразовых миграций. Значения всегда строки; типизация выполняется на границе через `get_int` / `set_int` и `get_text` / `set_text`.

### categories — группы приложений

| Колонка | Тип | Ограничения |
|---|---|---|
| `id` | INTEGER | Первичный ключ, автоинкремент |
| `name` | TEXT | NOT NULL |
| `sort_order` | INTEGER | NOT NULL, по умолчанию 0 |

Категории необязательны: приложение без категории имеет `category_id = NULL` и показывается в общем списке боковой панели.

## Каскады и целостность

Внешние ключи включены, и это определяет поведение при удалении:

- Удаление приложения через `apps` каскадно удаляет его строки в `stats` и `hours`. Но `remove_app` **дополнительно** удаляет их явно. Это избыточно при работающих внешних ключах, но защищает от ситуации, когда прагма не применилась.
- Удаление категории не удаляет приложения. `delete_category` сначала обнуляет `category_id` у всех её приложений, затем удаляет саму категорию. Даже если бы каскад сработал иначе, приложения остались бы без группы, а не исчезли.

Отдельно стоит `set_app_category` / `delete_category`: обе операции выполняются в одном контексте `with self._conn`, то есть в одной транзакции.

## Миграции колонок

`_migrate()` решает узкую задачу: добавить в `apps` колонки, которых не было в старых базах. Реализация прямолинейна — читается `PRAGMA table_info(apps)`, и если нужной колонки нет, выполняется `ALTER TABLE ... ADD COLUMN`:

- `sort_order` — появился вместе с перетаскиванием приложений;
- `category_id` — появился вместе с категориями.

Обе миграции идемпотентны и безопасны при повторном открытии: колонка добавляется один раз, дальше проверка находит её и ничего не делает. Обратных миграций (удаления колонок) нет — схема только расширяется.

## Валидация файла

`Database.validate(path)` — статический метод, который проверяет **чужой** файл перед загрузкой. Он не открывает `Database` и работает с отдельным временным соединением:

1. Файл должен существовать и быть именно файлом.
2. В базе должны быть таблицы `apps` и `stats`.
3. В `apps` должны быть колонки `id`, `name` и `exe_path`.
4. В `stats` должны быть колонки `app_id`, `day` и `seconds`.

Проверка требует именно **надмножества**: лишние таблицы и колонки допускаются, недостающие — нет. Соединение всегда закрывается в `finally`, а любое исключение трактуется как «файл не подходит».

Благодаря этой проверке загрузка произвольного SQLite-файла (например, базы браузера) невозможна — приложение откажется, не создавая пустую или испорченную статистику.

## Запись времени

Почти всё время попадает в базу через одну функцию — `add_activity_batch(entries)`, где каждая запись это кортеж `(app_id, day, hour, seconds)`. Функция выполняет для каждой записи два `INSERT ... ON CONFLICT ... DO UPDATE SET seconds = seconds + excluded.seconds`: один в `stats`, второй в `hours`.

Такая конструкция — upsert-инкремент — даёт две гарантии:

- Запись не требует предварительного чтения: строка создаётся или к ней прибавляется значение.
- Обе таблицы обновляются в одной транзакции, поэтому сумма по дням и сумма по часам не расходятся.

Пакетность важна для производительности: при сбросе буфера трекера может накопиться несколько десятков записей (несколько приложений × несколько часов), и все они проходят через одну транзакцию, а не через отдельную на каждую.

`add_time` и `add_hour` — раздельные варианты той же операции; они используются в служебных местах, например при разовом заполнении часов.

## Чтение

Методы чтения делятся на три группы.

**Точечные выборки** — `get_hours(app_id, day)` возвращает список ровно из 24 элементов, заполняя отсутствующие часы нулями; `get_day_stats(day)` возвращает словарь «приложение → секунды».

**Диапазоны** — `query_app_stats` и `query_hours_range` принимают границы, где обе границы включительные (`day >= ? AND day <= ?`); `query_stats` фильтрует необязательными границами по всем приложениям.

**Агрегаты** — `get_totals()` группирует всю статистику по приложению, `get_min_day()` возвращает самый ранний день в базе. Последний используется при первом запуске, чтобы определить начало истории.

`query_hours_range` возвращает не список, а словарь с ключом `(day, hour)`, потому что отсутствующие часы неотличимы от нулевых, и потребителю удобнее запрашивать по адресу.

## Настройки: has() и get_int()

Разница между этими методами — не стилистическая:

- `get_int(key, default)` возвращает `default`, если ключа нет **или** значение не приводится к целому.
- `has(key)` сообщает, существует ли ключ вообще, независимо от значения.

Смысл становится ясен на автозапуске. Три состояния требуют трёх разных действий:

| Состояние | Значение | Действие при старте |
|---|---|---|
| Включён | ключ есть, `1` | Перезаписать путь в реестре |
| Выключен явно | ключ есть, `0` | Удалить запись реестра, если она ведёт на текущий exe |
| Неизвестен | ключа нет | Усыновить существующую запись реестра |

`get_int("autostart", 0)` не различает второе и третье состояние — для обоих вернёт 0. Именно поэтому в `main.py` используется `db.has("autostart")`.

## Что важно помнить при правке

- `exe_path` сравнивается без учёта регистра на уровне схемы. При сравнении путей в коде это тоже нужно повторять — `app_path_taken` дополнительно нормализует путь через `os.path.normcase` и `os.path.normpath`, потому что `COLLATE NOCASE` в SQLite не нормализует разделители.
- `add_app` сигнализирует о дубле через `None`, а не исключением. Вызывающий код обязан это проверять.
- Любая запись времени должна идти через `add_activity_batch`, чтобы `stats` и `hours` не разошлись.
- Новая колонка в существующей таблице требует ветки в `_migrate()`. Просто дописать её в `_SCHEMA` недостаточно — старые базы её не получат.
- `validate` проверяет минимальный контракт, а не полную схему. Расширение схемы не ломает загрузку старых файлов, но и не гарантирует, что загруженная база создана этой же версией приложения.
