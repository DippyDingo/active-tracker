# Резервное копирование, экспорт и перенос базы

Вся статистика приложения живёт в одном файле SQLite. Поэтому операции вокруг этого файла — единственный способ сохранить данные при сбое или перенести их на другой компьютер. В коде есть три разных механизма, и они решают разные задачи.

| Механизм | Что делает | Куда пишет | Кто вызывает |
|---|---|---|---|
| `backup_to` | Консистентный снапшот работающей базы | `backup/tracker_<дата>.db` | Автоматически при старте |
| `export_to` | Копия для передачи пользователю | Путь, выбранный в диалоге | Вручную из меню |
| Загрузка базы | Подмена текущей базы на внешний файл | Путь из `config.json` | Вручную из меню |

## Почему нельзя просто скопировать файл

База открыта в режиме WAL (`PRAGMA journal_mode=WAL`), и это меняет правила копирования. В режиме WAL изменения сначала попадают в отдельный файл `-wal`, а не в основной `.db`. Если скопировать только `.db` при работающем соединении, копия может не содержать последних записей, а в худшем случае оказаться несогласованной.

Поэтому обе функции копирования начинают одинаково:

1. `commit()` — фиксируют текущую транзакцию.
2. `PRAGMA wal_checkpoint(TRUNCATE)` — вливают содержимое WAL в основной файл и обнуляют его.

Только после этого можно безопасно читать `.db`.

## Автоматический ежедневный бэкап

`_daily_backup` в `main.py` вызывается при каждом старте, но делает работу не чаще раза в сутки. День последнего бэкапа хранится в таблице `settings` под ключом `last_backup`: если там уже сегодняшняя дата, функция сразу возвращается.

Процедура:

1. Целевой путь — `backup/tracker_<дата>.db` внутри каталога данных.
2. Копия снимается через `db.backup_to(dest)`.
3. При успехе в `settings` пишется сегодняшняя дата.
4. Каталог `backup` сканируется на `tracker_*.db`, и все копии кроме трёх последних удаляются.

Вся операция обёрнута в `try/except` с логированием: сбой резервного копирования не должен мешать запуску приложения.

Ежедневные копии появились как ответ на конкретную проблему: раньше резервных копий не было вовсе, и повреждение файла или неудачная миграция означали безвозвратную потерю всей статистики.

## Как снимается консистентный снапшот

`Database.backup_to(dest)` устроен так:

1. Создаётся каталог назначения.
2. Выполняется `commit()` и `wal_checkpoint(TRUNCATE)`.
3. Копия пишется **во временный файл** `dest + ".part"` — не напрямую в цель.
4. Основной путь — `sqlite3.connect(tmp)` и `self._conn.backup(dst)`. Это API резервного копирования SQLite: оно снимает снапшот даже при обращении к базе из других потоков.
5. Если оно недоступно и выбросило исключение, есть запасной вариант — `shutil.copy2` исходного файла.
6. Существующая цель удаляется, временный файл переименовывается в неё.
7. При любой ошибке временный `.part` удаляется.

Схема «сначала `.part`, потом переименование» даёт важную гарантию: файл по целевому пути либо старый и целый, либо новый и целый. Наполовину записанной копии по этому пути не бывает — прерывание процесса оставит мусор в `.part`, а не повреждённую копию.

## Экспорт базы

Экспорт запускается из меню приложения (`_export_database` в `MainWindow`). Он ведёт себя так:

1. Скрывает всплывающее меню и **сбрасывает буфер трекера** (`tracker.flush()`), чтобы последние накопленные секунды попали в файл.
2. Предлагает имя по умолчанию `tracker_<сегодня>.db`.
3. При отсутствии расширения `.db` дописывает его.
4. Вызывает `db.export_to(path)` и показывает результат.

`export_to` использует `VACUUM INTO` — команду SQLite, которая создаёт полностью перестроенную и упакованную копию базы:

1. Если целевой путь совпадает с путём текущей базы, операция отклоняется — файл не будет скопирован сам в себя.
2. Выполняется `commit()` и `wal_checkpoint(TRUNCATE)`.
3. `VACUUM INTO` пишет во временный `.part`.
4. Существующая цель удаляется, `.part` переименовывается.

Отличие от `backup_to` принципиально: `VACUUM INTO` создаёт дефрагментированную базу без свободных страниц и без следов удалённых строк, поэтому файл получается компактнее и чище. Для передачи пользователю это правильный выбор; для быстрого ежедневного снапшота достаточно `backup`.

## Загрузка внешней базы

Загрузка (`_load_database`) — это не копирование, а подмена рабочей базы. Последовательность:

1. Пользователь выбирает файл `.db`.
2. Файл проверяется через `Database.validate(path)`. Проверка открывает базу и требует наличия таблиц `apps` и `stats` с нужными колонками. Просто «какой-то SQLite» не подойдёт — это защита от загрузки чужого файла.
3. Показывается подтверждение с предупреждением, что текущая статистика останется в прежнем файле и не удалится.
4. При согласии вызывается `_switch_db(path)`.

`_switch_db` делает переход аккуратно:

1. Создаётся `Database(path)` — новая база открывается до того, как старая закрыта.
2. `tracker.switch_db(new_db)` — трекер **сначала сбрасывает буфер в старую базу** (`flush()`), затем очищает буфер, меняет ссылку на базу и **перечитывает из неё настройки**: порог простоя, фоновый учёт. Сбрасывается также кеш запущенных процессов и всё состояние простоя.
3. Старая база закрывается через `self.db.close()`.
4. Новый путь сохраняется в `config.json` через `config.set_db_path(path)` — при следующем запуске откроется именно она.
5. Интерфейс перестраивается: сбрасывается выбор, вызываются `refresh_apps`, `_update_values`, `_update_status`.

Порядок в `switch_db` важен: сброс буфера идёт в **старую** базу, потому что накопленные секунды относятся к ней. Если поменять ссылку раньше сброса, время ушло бы не в ту базу.

## Что важно помнить при правке

- Любая копия должна предваряться `commit()` и `wal_checkpoint(TRUNCATE)`. Без этого копия может не содержать последних записей.
- Копия пишется в `.part` и переименовывается. Прямая запись в целевой файл ломает гарантию «либо старый, либо новый, но целый».
- Перед экспортом и переключением базы буфер трекера обязан быть сброшен — иначе до 15 секунд работы останутся вне файла.
- `validate` — не формальность: без неё пользователь мог бы загрузить произвольный SQLite-файл и получить пустое приложение.
- При переключении базы настройки трекера перечитываются из новой базы, поэтому порог простоя и фоновый учёт могут измениться сразу.
