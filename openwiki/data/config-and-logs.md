# Конфигурация и журналы

Приложение хранит данные в одном каталоге и разделяет их на три вида: файл настроек `config.json`, SQLite-базу со статистикой и журналы. Понимание того, что где лежит, важно при диагностике: часть проблем воспроизводится только состоянием в `config.json`, а часть — только содержимым базы.

## Каталог данных

Корень — `%APPDATA%\ActiveTracker`. Путь вычисляется из переменной окружения `APPDATA` с откатом на домашний каталог:

```
APP_DIR = Path(os.getenv("APPDATA", str(Path.home()))) / "ActiveTracker"
```

Каталог создаётся при первом обращении (`app_dir()` вызывает `mkdir(parents=True, exist_ok=True)`).

Имя каталога — `ActiveTracker` — наследство от прежнего названия приложения. Оно намеренно не менялось: смена пути означала бы, что у существующих пользователей статистика оказалась бы «потеряна», а установщик при удалении искал бы данные в другом месте.

Что лежит в каталоге:

| Путь | Назначение |
|---|---|
| `config.json` | Настройки, пути, состояние обновления и запуска |
| `tracker.db` | База по умолчанию (если не выбран другой путь) |
| `crash.log` | Журнал ошибок и фатальных сбоев |
| `nodexy_update.log` | Журнал работы помощника обновления |
| `nodexy_install.log` | Журнал установщика Inno Setup |
| `nodexy.lock` | Файл блокировки второго экземпляра |
| `install.lock` | Маркер идущей установки |
| `backup/` | Ежедневные копии базы |
| `updates/` | Скачанные установщики и кэш отката в `updates/prev/` |

## Файл config.json

### Атомарная запись

Запись устроена через временный файл и переименование:

1. Сериализуется JSON с `ensure_ascii=False` и отступом 2 — файл остаётся читаемым вручную, а кириллица в нём не превращается в escape-последовательности.
2. Данные пишутся в `config.json.tmp`.
3. Временный файл переименовывается в `config.json` через `Path.replace`.

Переименование в пределах одной файловой системы атомарно, поэтому читатель видит либо старый полный файл, либо новый полный файл, но не половину. При ошибке вызывается `log_error("config.write_config")` и возвращается `False` — вызывающий код обычно продолжает работу.

### Чтение

`read_config()` возвращает словарь или **пустой словарь** при любой проблеме: отсутствии файла, ошибке разбора, если корень JSON — не объект. Это осознанная стратегия: повреждённый `config.json` трактуется как «настроек нет», и приложение предлагает создать или выбрать базу заново, вместо того чтобы падать.

### Полный список ключей

Ключи `config.json` пишутся и читаются в разных местах, и их удобно разделить по назначению.

**Пути и первые запуски**

| Ключ | Кто пишет | Кто читает |
|---|---|---|
| `db_path` | `set_db_path` | `get_db_path` |
| `first_launch` | `main._ensure_first_launch` | `main._open_stats`, панель статистики |
| `rollback_safe_mode` | `updater.startup_processing` | `MainWindow._apply_rollback_safe_mode` |

**Состояние обновления**

| Ключ | Структура | Назначение |
|---|---|---|
| `update_pending` | `{version, notes, file, kind, page, attempts}` | Скачанный и ожидающий применения установщик |
| `last_update` | `{version, notes, file, seen}` | Заметки последнего успешного обновления |
| `boot_check` | `{version, fails, clean}` | Счётчик неудачных запусков для отката |

Ключ `update_pending` — самое насыщенное состояние. Поле `kind` различает механизмы обновления: действует только `"installer"`, записи старого механизма (замена exe на месте) при старте отменяются. Поле `attempts` считает неудачные попытки установки, поле `page` хранит ссылку на страницу релизов для сообщения об исчерпании попыток.

`last_update` с полем `seen` управляет показом окна «Что нового»: если заметки версии ещё не помечены как просмотренные, приложение предлагает их показать. `whatsnew_unseen()` и `mark_whatsnew_seen()` работают с этим полем.

`boot_check` — состояние защиты от зацикливания. Поле `clean` отличает штатный выход от падения. Пока приложение работает, `clean` остаётся `False`; `mark_clean_exit()` ставит `True` при нормальном закрытии.

**Настройки в базе, а не в файле**

Часть пользовательских настроек живёт не здесь, а в таблице `settings` базы: порог простоя (`idle_threshold_minutes`), фоновый учёт (`background_counting`), тема (`theme`), автозапуск (`autostart`), маркеры миграций (`hours_backfilled`, `last_backup`). Выбор объясняется просто: эти настройки относятся к конкретной базе, и при её переносе логично перенести их вместе с данными. Состояние обновления, наоборот, относится к установке приложения, а не к базе, поэтому лежит в файле.

### Отличие has() от get_int()

В базе есть пара методов, разница между которыми важна и легко упускается:

- `get_int(key, default)` возвращает значение или `default`, если ключа нет.
- `has(key)` сообщает, существует ли ключ.

Различие нужно там, где ноль и отсутствие — разные вещи, например при синхронизации автозапуска: `autostart = 0` (пользователь явно выключил) и отсутствие ключа (приложение ещё не знает о состоянии реестра) требуют разных действий.

## Журналы

### Три файла и их владельцы

Журналы пишут разные процессы, и это стоит различать при диагностике:

- `crash.log` — само приложение: ошибки Python и фатальные сбои.
- `nodexy_update.log` — помощник `REDISUpdater.exe`, с отметками времени.
- `nodexy_install.log` — установщик Inno Setup, подключается флагом `/LOG=`.

Ошибка установки, таким образом, оставляет след в двух последних файлах, а не в `crash.log`.

### Ротация

`rotate_logs()` вызывается при старте **до** открытия журналов на запись. Правило простое: если файл больше 2 МБ, он переименовывается в `<имя>.old`, а прежний `.old` перезаписывается. Ротации подлежат ровно три файла: `crash.log`, `nodexy_update.log`, `nodexy_install.log`.

Ошибки на каждом шаге подавляются отдельно (`OSError` на файле — `continue`), поэтому занятый другим процессом журнал не помешает повернуть остальные.

### crash.log и faulthandler

`crash.log` открывается в режиме дозаписи на уровне импорта `main.py`, и в него сразу направляется `faulthandler`. Это даёт то, чего не может дать `sys.excepthook`: faulthandler перехватывает фатальные сигналы и падения в нативном коде, включая segfault внутри Qt, и печатает стек Python на момент сбоя.

`sys.excepthook` дополняет это: он пишет разделитель с ISO-временем и полный traceback через `traceback.print_exception`, после чего делает `flush`. Без явного `flush` последние строки могли бы остаться в буфере и потеряться при аварийном завершении.

`config.log_error(message)` используется в местах, где ошибку нужно зафиксировать, не прерывая работу: сбой записи конфига, ошибки трекера, операции обновления. Он пишет заголовок с временем и сообщением, затем `traceback.format_exc()`. Вызывается из `except`-блоков, поэтому traceback актуален.

## Что важно помнить при правке

- `read_config()` намеренно возвращает пустой словарь при любой ошибке. Код, который рассчитывает на наличие ключа, должен иметь разумное поведение по умолчанию.
- Запись только через `.tmp` + `replace`. Прямая запись в `config.json` может оставить обрезанный файл при сбое питания.
- Ключи `boot_check` и `update_pending` взаимосвязаны: `startup_processing` несколько раз перечитывает конфиг, потому что логика выше могла его изменить, а запись устаревшего снимка воскресила бы уже отменённое обновление.
- Перед добавлением нового журнала стоит добавить его в `_LOG_FILES`, иначе он будет расти без ротации.
- `crash.log` открывается один раз и держится открытым; переименование файла во время работы не переключит уже открытый дескриптор.
