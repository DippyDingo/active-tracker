2. Общая информация о проекте

Приложение Nodexy — локальный Windows-трекер времени, проведённого в различных программах.
Основные технологии:
- Python;
- PySide6;
- SQLite;
- pywin32;
- Pillow;
- psutil;
- Win32 API.

Основные модули проекта:
- main.py — запуск приложения и жизненный цикл;
- app/tracker.py — учёт активности и накопление времени;
- app/db.py — SQLite и операции с данными;
- app/config.py — config.json и путь к базе;
- app/win32_utils.py — Win32 API, активное окно, процессы, иконки;
- app/installed_apps.py — обнаружение установленных программ;
- app/ui/main_window.py — главное окно, карточки, категории, трей;
- app/ui/add_dialog.py — добавление приложений и фоновое сканирование;
- app/ui/stats_panel.py — подробная статистика;
- app/ui/modal.py — модальные окна;
- app/ui/widgets.py — виджеты и графики;
- build_exe.bat — сборка PyInstaller.

3. Итоговый вердикт аудита

Субъективная оценка текущего состояния: 6/10 для личного приложения.

Положительные стороны:
- архитектура в целом подходит для локального личного приложения;
- нет неоправданной enterprise-сложности;
- код разделён на трекер, базу, Win32-интеграцию и UI;
- SQL-запросы в основном параметризованы;
- включены SQLite foreign keys;
- используется буферизация времени;
- есть кэширование списка процессов;
- сканирование установленных программ выполняется в отдельном потоке;
- есть экспорт базы, системный трей и журнал ошибок.

Главная причина снижения оценки — риски неправильного учёта времени и проблемы на переходах между состояниями: удаление приложения, смена базы, полночь, простой, ошибки сохранения, завершение фонового потока и повторный запуск.

4. Критичные и высокоприоритетные проблемы

4.1. Удаление приложения с непустым буфером

Файлы и места:
- app/ui/main_window.py:1126–1140;
- app/tracker.py:103–113;
- app/db.py:32–44, 135–138.

Сценарий:
- у удаляемого приложения ещё есть накопленные секунды в Tracker._buffer или оно находится в Tracker._idle_apps;
- приложение удаляется из таблицы apps;
- затем refresh_apps() вызывает tracker.flush();
- трекер пытается записать секунды уже удалённого app_id.

Последствия:
- возникает ошибка внешнего ключа SQLite;
- буфер проблемного приложения может остаться навсегда;
- последующие flush могут регулярно завершаться ошибкой;
- записи других приложений после проблемной записи могут не сохраниться;
- обновление интерфейса может оборваться.

Рекомендация:
- добавить операцию Tracker.forget(app_id);
- убрать приложение из _buffer, _idle_apps, current_ids, current_app_id и _tracked;
- согласовать порядок удаления из трекера и базы;
- простого flush перед удалением недостаточно, потому что старый ID может остаться в состоянии простоя.

4.2. Раздельные транзакции для дневной и почасовой статистики

Файлы и места:
- app/tracker.py:107–112;
- app/db.py:190–208.

Проблема:
- add_time() и add_hour() используют отдельные транзакции/коммиты;
- дневная запись может сохраниться, а почасовая — завершиться ошибкой;
- если процесс продолжает работать, буфер не уменьшается и при повторном flush те же секунды могут повторно прибавиться к дневной статистике.

Рекомендация:
- сделать один метод базы данных, который обновляет stats и hours в одной транзакции;
- уменьшать буфер только после успешного коммита;
- не списывать буфер заранее, иначе при ошибке можно потерять время.

4.3. Некорректное распределение по часам и дням

Файлы и места:
- app/tracker.py:103–155;
- main.py:43–57.

Проблема:
- буфер хранит app_id и секунды, но не дату/час начисления;
- flush берёт текущий час в момент записи;
- задержка или idle-gap может быть записан в неправильный час;
- при flush после полуночи часть времени за предыдущий день может попасть в час 0 предыдущего дня;
- idle-gap, пересекающий полночь, целиком может попасть в новый день;
- _backfill_today_hours() равномерно распределяет недостающие секунды и фактически создаёт приблизительную, а не реальную почасовую историю.

Рекомендация:
- хранить буфер с ключом вроде (app_id, day, hour);
- разделять интервалы по границам часа и суток;
- не выдавать эвристический backfill за фактическую историю либо явно помечать его как оценку.

4.4. Отсутствует защита от второго экземпляра

Файлы:
- main.py:73–102.

Проблема:
- не найден single-instance guard;
- две копии приложения могут открыть одну базу;
- обе копии будут одновременно начислять время.

Последствие:
- время может удваиваться или утраиваться.

Рекомендация:
- добавить механизм единственного экземпляра через QLocalServer/QSharedMemory или эксклюзивный lock-файл;
- повторный запуск должен активировать уже открытое окно.

4.5. Экспорт базы неатомарен

Файлы и места:
- app/db.py:101–111;
- app/ui/main_window.py:1034–1054.

Проблема:
- существующий файл назначения удаляется до выполнения VACUUM INTO;
- если экспорт не удался, старая резервная копия уже потеряна;
- нет явного запрета экспортировать поверх текущей рабочей базы.

Рекомендация:
- экспортировать во временный файл;
- после успешного завершения делать атомарную замену через os.replace;
- запрещать путь активной базы в качестве файла экспорта.

4.6. Небезопасное завершение потока сканирования

Файлы и места:
- app/ui/add_dialog.py:24–32, 205–207, 278–280;
- app/ui/modal.py:102;
- app/ui/main_window.py:986–1008, 1234–1247.

Проблема:
- _ScanWorker является QThread с родителем AddPanel;
- shutdown() ждёт максимум 5 секунд, но не проверяет результат ожидания;
- после этого панель может быть удалена при ещё работающем потоке;
- при закрытии приложения aboutToQuit явно останавливает только Tracker, а не сканирование.

Последствия:
- возможна ошибка «QThread: Destroyed while thread is still running»;
- потенциально нестабильное завершение приложения;
- GUI может блокироваться на ожидании.

Рекомендация:
- добавить кооперативную отмену сканирования;
- не уничтожать владельца потока до его завершения;
- корректно завершать worker при выходе;
- не использовать принудительное убийство потока.

5. Дополнительные проблемы среднего приоритета

5.1. Несовпадение индексов периодов

В main_window.py и stats_panel.py используются разные списки PERIODS.
Из-за передачи индекса:
- «Месяц» в главном окне может открываться как «2 недели»;
- «Всё время» может открываться как «Месяц».

Рекомендация: использовать общий enum/идентификатор периода, а не позицию элемента в разных списках.

5.2. StatsPanel устаревает после открытия

StatsPanel читает историю, часы и сегодняшнее время в конструкторе. После открытия панель не обновляется вместе с Tracker.

Кроме того:
- today_live учитывает pending_seconds;
- почасовые данные берутся отдельно и могут не включать pending-секунды.

Рекомендация: обновлять панель по сигналу изменений и использовать единый источник текущего времени.

5.3. Смена базы не полностью сбрасывает состояние Tracker

В Tracker.switch_db() очищаются буфер и кэш, но не все состояния idle/current.
Старые app_id могут попасть в новую базу.

Рекомендация: при смене базы полностью сбрасывать _idle, _idle_apps, _idle_since, _last_active_at, current_ids и current_app_id.

5.4. Свёрнутые категории могут раскрываться при фильтрации

В main_window.py:_apply_filter() видимость строк меняется без полного учёта состояния _collapsed.

Рекомендация: вычислять видимость как комбинацию условий «совпадает с фильтром» и «категория не свёрнута», за исключением поведения, которое специально нужно для найденного результата.

5.5. Поверхностная проверка загружаемой БД

Database.validate() проверяет наличие нескольких таблиц, но не проверяет обязательные столбцы, версию схемы и совместимость миграций.

Рекомендация: добавить schema_version и проверку структуры.

5.6. Конфигурация глотает ошибки

app/config.py:28–35 подавляет ошибки записи config.json.
Если db_path не сохранился, приложение может завершиться без понятного сообщения.

Рекомендация: атомарная запись через временный файл, проверка JSON и уведомление пользователя при ошибке.

5.7. Поведение без системного трея

В main.py установлено setQuitOnLastWindowClosed(False). Если трей недоступен и окно закрывается, процесс может остаться работать без окна и без способа его открыть.

Рекомендация: при отсутствии трея закрывать QApplication явно.

5.8. Сбой сканирования скрывается

В add_dialog.py исключение при сканировании превращается в пустой список без записи в лог.
Пользователь видит «0 приложений» и не понимает, что произошла ошибка.

Рекомендация: логировать исключение и показывать понятный статус сканирования.

5.9. Ошибка чтения FileDescription

Файл: app/win32_utils.py:61–73.

Документация Microsoft указывает, что VerQueryValueW возвращает длину строкового значения в символах. Текущий код делит length.value на 2 при чтении FileDescription, поэтому название программы может быть обрезано.

6. Производительность: только риски, без замеров

Фактические тормоза не измерялись. Статически видны потенциальные источники нагрузки:
- _on_tick() обновляет скрытый интерфейс, пока окно находится в трее;
- получение списка процессов и часть операций SQLite выполняются в GUI-потоке;
- MiniChart имеет бесконечную декоративную анимацию;
- создание всех строк списка установленных программ происходит одним проходом в GUI;
- иконки и обработка большого количества виджетов могут вызвать кратковременный фриз.

Рекомендация:
- сначала измерить длительность операций;
- не обновлять скрытые карточки;
- останавливать декоративные анимации, когда они не видны;
- создавать большие списки постепенно;
- тяжёлые операции выносить в фон только после подтверждения замером.

8. Проблемы сборки

Файл: build_exe.bat.

Наблюдения:
- выводится сообщение о готовности без проверки errorlevel PyInstaller;
- команда собирает Nodexy, а сообщение говорит ActiveTracker.exe;
- зависимости имеют только ограничения >=, поэтому состав окружения может плавать между установками.

Рекомендация:
- проверять код завершения сборки;
- привести имя в сообщении и параметрах к одному варианту;
- зафиксировать проверенные версии зависимостей или хранить lock/requirements freeze.
